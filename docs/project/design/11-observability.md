Muru reports three kinds of data: metrics for continuous measurements, logs for per-request and application output, and events for changes of state. Each has one source of truth and several consumers.

## 11.1 Metrics

Prometheus metrics are served by the daemon on the admin listener (/metrics on the JSON gateway) and, optionally, on a dedicated metrics listener bound to an internal address, never on public listeners by default. Each edge process reports its metrics to the daemon, which aggregates them, so one scrape covers a node. Names use the muru_ prefix and labels app, release, group, mount, route and host where relevant.

| Area | Examples |
| --- | --- |
| Requests | muru_requests_total by status class and reason, muru_request_duration_seconds histograms (queue, application, total), muru_requests_in_flight, muru_request_retries_total, muru_access_log_dropped_total, muru_auth_requests_total by result |
| Capacity | muru_queue_depth, muru_slots_busy and muru_slots_total (each by side, `threads` or `loop`, since a request is held against the side that runs it, section 5.1), muru_capacity_utilisation (busy slots over slots of the busier side, sampled every second and averaged over 30 s, the saturation signal for an autoscaler such as an HPA or KEDA, since CPU stays low while an I/O-bound application's slots are full), muru_websocket_connections, muru_websockets_closed_total by side and how, muru_websocket_duration_seconds; muru_handoffs_total by the interface a request was handed to (section 6.14) |
| Workers | muru_worker_requests_total and muru_worker_requests_in_flight as each worker last reported, muru_worker_sync_threads_busy and muru_worker_sync_threads for a worker with an event loop (the busy threads and the size of each pool synchronous code runs on, by pool: loop, anyio or asgiref, section 6.6), muru_worker_cpu_seconds_total, muru_worker_memory_bytes by kind (uss, pss, rss), muru_gil_wait_seconds, muru_loop_lag_seconds and muru_handoff_queue_wait_seconds histograms, muru_worker_recycles_total by reason, muru_worker_exits_total by reason |
| Garbage collection | muru_gc_collections_total, muru_gc_seconds_total and muru_gc_collected_objects_total by generation, muru_gc_pause_seconds histogram by generation and by whether requests were in flight |
| Scaling | muru_scaling_decisions_total, muru_workers_desired, muru_workers_ready, muru_churn_reaps_total |
| Edge | muru_connections_open, muru_connections_refused_total, muru_tls_handshakes_total by result, muru_snapshot_version, muru_upstream_health |
| Bodies and uploads | muru_upload_spool_bytes |
| Clients | muru_requests_total by client_class, muru_rate_limited_total by limit, client class and action |

**Garbage collection.** CPython's cyclic collector pauses the whole process while it runs: on a regular build the collecting thread holds the GIL, on a free-threaded build the collector stops every thread. The gc.freeze() sequence of section 6.2 keeps the preloaded heap out of a worker's collections, and what remains is measured rather than guessed at. Each worker's runtime registers a `gc.callbacks` entry that notes the time and the requests in flight when a collection starts and, when it stops, records the pause, the generation and the objects freed, keeping pauses with requests in flight apart from pauses that cost nothing. The figures travel with the worker's status line, as its CPU time and GIL waits do, and are exported for each worker: counters of collections, time collecting and objects freed by generation, and a histogram of pauses by generation and by `requests` (`in_flight` or `none`) over the signal bounds of section 7.3. The generation label is what the interpreter reports: `0`, `1` or `2` on a build with generations, `full` on a free-threaded build, whose collector takes the whole heap each time. `muructl debug memory` and the dashboard's worker view show the same figures beside the gc counts (section 11.7), and the scaling diagnosis names collection when it takes a tenth of the workers' time or more (section 7.3). The callback costs two calls into the extension, a monotonic clock read and a few atomic additions per collection, about a microsecond against the tens of microseconds or more an automatic collection takes, so it is on in every worker with no setting (ADR 0038).

Some figures are read from a family above rather than exported again: the queue wait is the `queue` phase of muru_request_duration_seconds, a worker's CPU ratio is `rate()` over muru_worker_cpu_seconds_total, and bodies refused for their size are muru_requests_total with the `body_too_large` reason, so there is no muru_queue_wait_seconds, muru_worker_cpu_ratio or muru_body_rejections_total. The edge's own CPU time per thread is not exported.

The dashboard reads the same values from in-memory history. OTLP metric export is optional.

## 11.2 Access logs and application logs

- Access logs are structured (JSON by default, or a configurable text format) with request id, host, route, release, group, worker, snapshot version, status and reason, bytes, and timings for queue, application and total, plus internal redirect hops.
- **The format and the file.** `access_log_format` in `[logs]` and on a virtual host is `json`, one object a line, or `combined`, the combined log format of Apache and nginx; a host's replaces the node's for its records. A host's `access_log_file` names a file in the daemon's log directory that takes its records in place of `access.log`: a plain name, not one of the daemon's own, and hosts that share one give the same format. Both travel on the host's access log choice in the snapshot, the file as a path, so an apply or a reload changes them without a restart. The edge's writer thread opens such a file when a line first wants it and again after a reopen, and the daemon rotates it with `access.log`. A combined line has the client, the UTC time, the request line, the status, the bytes sent, the Referer and the User-Agent, which a record keeps only while some record is written in that format; the identity and user fields are hyphens, and a WebSocket has its handshake's line alone. Every JSON record names its virtual host as `virtual_host`, the host's configured name, which is how `muructl logs --access --host NAME` picks a host's records out of `access.log` when the host names no file; with a file it reads that, printing a text format as written. A format template with named fields is not offered (section 20.14).
- Which records are written is a filter apart from where they go: on, errors (4xx and 5xx responses, requests at least a slow threshold, and WebSockets that closed other than normally or going away) or off, less path patterns left out. Every record is counted in the metrics and kept in the in-memory ring whatever the filter says. Under the daemon the `[logs]` table sets the node's filter, and a virtual host's table and an application's table may each set their own, the application's laid over its host's and the host's over the node's key by key with the excluded paths adding up (ADR 0049); a request the edge answers before an application is chosen is written by its host's. All travel in the snapshot, so `muructl daemon reload` and `muructl apply` change what the running edge writes without a restart. A development run and `muructl serve` take theirs from their flags and tables.
- `muructl logging access MODE [--app APP] [--path PATTERN]... --for DURATION` changes what is written for a period and reverts on its own, as `muructl logging level` does for loggers (section 11.4). A change covers one application or every one, and the paths matching its patterns or every path; the newest in force that covers a request decides, with the slow threshold of the filter it replaces, and one that names paths writes them even where the filter excludes them. The daemon keeps the changes in memory and sends those in force in every snapshot, each with its end, which the edge honours without being told, so a change cannot outlast its period and a daemon that starts again has none; it records access_log.changed and access_log.reverted. A development run and `muructl serve` change their own edge's filters through the admin socket and print the same events. `--reset` puts the changes back, and the command without a mode lists those in force with the time each has left.
- Worker stdout and stderr are per-worker pipes. The host creates them at fork and passes the read ends to the daemon over the control socket. The log collector tags lines with application, release, group, worker and stream, keeps ring buffers for the CLI and dashboard, and writes sinks. Workers are line-buffered. In development mode there is no collector yet, so the host itself relays the pipes to its standard error, each line tagged with the worker's index and, for stdout, the stream (muru.worker[0]: and muru.worker[0].stdout:).
- Sinks: terminal (development), journald (default under systemd), files.

## 11.3 Log rotation

- Writer threads in long-lived processes own every file, so rotation is a handle swap and never involves workers or restarts. Files use O_APPEND, so concurrent edge writers during handoff never interleave within a line.
- Built-in rotation: size and time based, retention count and age, configurable backup names, background compression (gzip or zstd).
- External rotation: logrotate renames files, then runs muructl logs reopen (or sends SIGUSR1). reopen_on_rename detects renames without a signal. copytruncate works but can lose lines. rotate = 'external' disables built-in rotation, and configurations where both would rotate a file are rejected.
- Applications that open their own log files get an on_reopen_logs control message (muructl logs reopen --workers), whose default hook makes logging file handlers reopen on next emit.
- Backpressure never reaches requests: the access log drops and counts records when stalled; application output uses a large drop-oldest queue by default, or blocks if configured. The edge's access log lines go to a writer thread of their own over a bounded queue (16k lines), which gathers what is waiting into writes of up to 64 KiB and reopens the file in order with the lines; a request's task only queues its line, and a line that finds the queue full is dropped and counted in muru_access_log_dropped_total, the writer saying how many once it has caught up. The edge and a development run wait for the queue to empty before they exit.

## 11.4 Python logging defaults

- Before importing the application, the host sets the root logger level and replaces logging.lastResort with a platform handler using the configured format (a format string or json) that writes to stderr. A lastResort handler is used only when no handler exists in a logger's hierarchy, so basicConfig and dictConfig behave exactly as without Muru.
- Every record carries the request id and the Muru tags, through a record factory installed with the defaults, as `muru_request_id`, `muru_app`, `muru_release`, `muru_group` and `muru_worker`, so an application's own format can use them; the prefix keeps them apart from an application's `extra`, which `logging` refuses to let overwrite an attribute the record already has (OpenTelemetry's logging instrumentation prefixes its own the same way). The json format writes the request id as `request_id`. Optional: logging.captureWarnings and a per-logger level map.
- Precedence: Python default, daemon configuration, application, release, the application's own configuration, then time-limited runtime overrides (muructl logging level RELEASE --logger NAME --level DEBUG --for 15m).
- MURU_LOG_LEVEL, MURU_LOG_FORMAT and muru.logging.default_config() let applications adopt the platform defaults explicitly.
- The standard format has no time, because Muru adds one where the output wants it (section 11.8); the json format carries the record's creation time in its `time` field.

## 11.5 Event stream

- One stream of state changes: configuration, releases and rollouts, host and worker lifecycle, recycles and timeout kills, scaling decisions, drains, schedules, edge and daemon upgrades, certificates and warnings.
- CloudEvents 1.0 JSON with a node-wide sequence number (muruseq), subject (app/release/group/worker), actor (user identity or component), correlation ids per rollout or deploy, and a level (info, notice, warning, error). Events never contain secrets or request data. Event types are listed in Appendix C.
- Pull: WatchEvents over gRPC, or Server-Sent Events on the JSON gateway, resumable from a sequence number. muructl events --follow uses the same stream.
- Push sinks with their own filters: webhooks (HMAC-signed, persistent outbox, at-least-once, deduplicate by id), OTLP log records (and spans for rollouts and deploys), journald or syslog, and JSON lines files.
- Retention: 7 days by default, capped by size. The audit log is the long-retained subset initiated through the API.

## 11.6 Tracing

The edge creates a server span per request and forwards W3C traceparent and tracestate to the application in the request head, so OpenTelemetry instrumentation in the application continues the trace. Edge spans and optional worker spans (queue wait, dispatch) are exported over OTLP when configured. Rollouts and deploys can be exported as spans so they appear on the same timeline.

## 11.7 Debugging and live inspection

Every worker has a control connection to its host, and the host to the daemon, so the admin API can reach into any worker of any release: a laptop run, a release in a container, a worker under another user or, in phase 5, on another node. The `muructl debug` commands use that path to find out what a worker is doing and, when needed, to step into it. They share one shape: `muructl debug VERB TARGET [--worker N] [--for DURATION]`, where TARGET is a release or an application, the default is every worker of the release, and the output streams back over the same admin API stream it was requested on, so nothing opens a port.

**Two mechanisms.** Everything below is built on one of these.

- *From outside the process.* Python 3.14 added PEP 768, which lets another process read a running interpreter's frames and run code in it at a safe point; the sampling profiler (`python -m profiling.sampling`), `python -m asyncio ps` and pdb's remote attach are built on it. These need no cooperation from the worker and cost it nothing until used, so they work on a worker that is hung or spinning. The host is the agent: it is the parent, runs as the same user and in a container is PID 1, so it has the rights PEP 768 needs without anything being opened up. On interpreters before 3.14 these commands fall back to the in-process mechanism where one exists and are otherwise unavailable.
- *From inside the process.* A control thread in the runtime library, created by the extension and never holding the GIL while idle, that the host can ask to run named operations: sys.monitoring, tracemalloc, faulthandler, gc, importlib, logging. It stays responsive while the GIL is contended, because it is a Rust-side thread that attaches only to do its work.

**What a worker is doing now.**

- `muructl debug stacks`: the Python stack of every thread, with the request id, path and elapsed time of the request each application thread is serving, from the bridge's own bookkeeping. Taken from outside, so it works on a hung worker, with a faulthandler fallback when the interpreter cannot be read. Across a release the stacks are merged, so sixteen workers waiting on the same lock show as one stack with a count.
- `muructl requests`: the requests in flight now, from the edge, which sees every request including those no worker has yet (issue 379): counted by worker group, since the edge queues per group, as those queued for a slot, those holding a thread of the group's threads and those on an event loop, each with the age of the oldest, the columns of the sides the release has, with the same one-word headers as `debug status` for the same figures; and with `--list` each request, the oldest first by its start time, with its age, state (queued or running), kind as of now (`wsgi`, `asgi`, either with `streaming` once its head asked for immediate flushing, `grpc`, `handoff` once DETACH moved it across, `upstream` for a managed server; `-` while queued), worker, method and target, client and request id. An accepted WebSocket leaves the listing for `muructl websockets`, and a static file, answered at once, is never in it. The edge keeps the listing beside each request's access log record, registered when the record is made and removed when the request ends, spread over sixteen maps by a number of its own so that arrivals and ends do not serialise on one lock, and measured under load before it landed; what a request is charged to is what the edge charged (the worker's side from HELLO, moved by a handoff), which is what `debug status` shows from the worker's own table, so the two can differ for a worker serving both interfaces until the edge's accounting agrees (issue 362). Served by the daemon, a development run and `muructl serve` over the admin API (`ListRequests`), with `--json` and an MCP tool beside `websockets`.
- `muructl debug tasks`: for ASGI workers, the asyncio task tree with what each task awaits, from `asyncio ps` and `pstree`, and the event loop lag.
- Automatic capture: when a request passes its soft timeout (section 7.6), before a worker is killed for a hard timeout, and before a worker is recycled for memory (section 7.7), the host takes the stack dump first and attaches it to the event, so "worker killed after 60 s" reads "worker killed after 60 s, waiting in a database connect here".

**Profiling for a period.**

- `muructl debug profile --for 30s`: sampling with the standard library's profiler, of one worker or every worker of a release at once, written locally as collapsed stacks for a flame graph or as pstats. Safe on production, which is the point of sampling: at the default interval a profile costs a busy worker nothing measurable, whether read from outside (Linux, Python 3.15 and later) or taken by a thread of the worker, which with the GIL waits its turn for the interpreter and on a free-threaded build pauses the other threads for the moment each sample takes; at a 1 ms interval a busy worker loses a few percent (issue 374).
- `muructl debug trace --for 10s`: in-process sys.monitoring for exact call counts and times when sampling is too coarse. It costs the worker something, so it refuses a worker above a load threshold unless forced; the worker keeps serving while it runs, so the trace sees the requests it takes meanwhile.
- `--requests N --path PREFIX`: profile or trace only the next N requests matching a path or header rather than everything on a busy worker.

**Memory.**

- `muructl debug memory`: resident size, gc generation counts and the collections timed since the worker started (how many, how long, what they freed, and how many ran while requests were in flight, by generation; section 11.1) at any time, and object counts by type. With `--trace --for 30s`, tracemalloc for the period and the top allocation sites, or a snapshot diff between two points.
- Before a memory recycle (section 7.7) the host can take a snapshot of the worker it is about to replace, so the leak is attributed rather than just survived.

**Stepping in.**

- `muructl debug attach`: a pdb session in a worker, carried as a byte stream over the admin API. The worker is drained and pinned while the session lasts, its timeouts are suspended, the thread being debugged stays off the pool, and a maximum session length ends a forgotten session. With `--dap` the same tunnel carries the Debug Adapter Protocol for debugpy, so an IDE attaches through muructl rather than through a port.
- `breakpoint()` in application code: the runtime library's breakpoint hook waits for a `muructl debug attach`, raising an event that names the worker, file and line, and gives up after a timeout. Outside Muru the hook does nothing special, so the call is safe to leave in.
- `muructl debug exec -- CODE`: run a snippet in a worker and return its output. Admin role, audited, and off in production unless enabled.

**State and configuration.**

- `muructl debug inspect`: the worker's sys.path, loaded modules with versions and file paths, environment with secrets redacted (the value of a key with SECRET, TOKEN, PASSWORD, PASSWD, KEY, CREDENTIAL or AUTH in its name or ending in _DSN, and the password of a URL under any other key), resolved settings, open descriptors and sockets, and thread names.
- `muructl logging level` (section 11.4) changes a logger's level for a period and reverts on its own.
- faulthandler is enabled in every worker with its output routed to the log collector, so a crash in a C extension leaves a Python traceback rather than nothing.

**Phase 2 interim.** The first slice (ADR 0025) builds the in-process mechanism: a control thread in the runtime library on a socket pair inherited at fork, the host relaying the daemon's requests, and faulthandler on SIGQUIT for a worker that cannot answer in time. Stacks are taken from inside until the PEP 768 reader is added for Python 3.14 and later.

**Scope and limits.** Every command is an admin-role operation (section 10.6), is recorded in the audit log, and works through the daemon's existing channels, so nothing listens anywhere new. Reading another process needs the right ptrace permissions: the same user suffices on Linux with the default ptrace scope, while macOS allows it only to root (ADR 0028), and in a container the host does the reading from inside. Status, stacks, tasks, inspect, logging levels and faulthandler arrive with the daemon in phase 2; profiling, tracing, memory tracing, attach, exec and the automatic captures follow in phase 3 with the soft timeouts and memory policy they build on (section 14.5).

- **Details fixed by the implementation.** Profiling, tracing, memory and exec go the same way as the phase 2 commands, through the runtime's control thread (ADR 0025), so they work on every supported interpreter: `profile` samples `sys._current_frames()` from that thread every `--interval` (10 ms) for `--for` (10 s), leaving out the thread answering and the worker's main thread, which waits in the runtime, and returns collapsed stacks labelled `qualname (file:first line)` under the thread's name, which muructl merges across workers and writes heaviest first, with the busiest leaf functions on standard error; `trace` takes sys.monitoring's profiler tool id for PY_START, PY_RESUME, PY_RETURN, PY_YIELD and PY_UNWIND (Python 3.12 and later) and reports inclusive time and calls per function, refused when the requests on the worker's threads exceed half its threads, or those on its event loop half its concurrency, each side measured against its own slots (section 5.1), unless `--force`; `memory` reports rss, pss and uss as section 7.7 measures them, gc counts and statistics, and the commonest types among gc's objects, and with `--trace` compares tracemalloc snapshots at the start and end of the period by line, stopping tracemalloc after unless it was already on; `exec` parses the code, runs it in a fresh namespace with standard output and error captured, and returns its output and the repr of a final expression, refused unless the daemon's `[daemon]` table sets `debug_exec = true`. An operation over a period asks the host to wait its length plus 5 s and the daemon plus 15 s more. `profile`, `trace`, `memory` and `exec` are events (`debug.*`, exec at warning level with the first 200 characters of its code), which stand as the audit record until there is an audit log. The soft timeout's watchdog reads the overdue thread's innermost three frames, without opening source files, before it interrupts the thread, logs them, and sends the host a `request.soft_timeout` event naming the worker; for an ASGI request, whose task is cancelled, the event names no place. Before a hard-timeout kill the host asks the worker for its stacks, logs them and adds where the oldest request was to the `worker.timeout_killed` event, sending SIGQUIT only when the worker does not answer within a second; before a memory recycle it asks for the five commonest object types and adds them to `worker.recycled`. `breakpoint()` in a worker records where it stopped, raises `debug.breakpoint`, takes its request out of the soft and hard timeouts, and waits for an attach for 60 s or its `timeout` argument, then carries on with `debug.breakpoint_expired`; a `PYTHONBREAKPOINT` in the environment keeps its own hook. In a coroutine it holds the worker's event loop while it waits, as pdb does, and its request stays under the timeouts, since an ASGI request has no thread of its own to exempt. `muructl debug attach` carries the session line by line over the Debug operation (`attach`, `attach_io` and `detach`, with `breakpoints` listing those waiting), each line answered with what pdb wrote since and the session polled every 300 ms meanwhile; without `--worker` it takes the first worker with a breakpoint waiting. The session takes the oldest breakpoint waiting, or else starts a thread of its own; `continue` with no breakpoint left, `quit`, the end of input, an hour in all or ten minutes without a line end it, the operator's breakpoints cleared so the code goes on. A debugger runs code in the worker, so attach is refused unless `debug_exec = true`, as exec is; a session is `debug.attached` (warning) and `debug.detached`. Between an attach the worker accepts and its last session's `debug.detached`, the host leaves the worker out of the sockets it announces and pins it, recycling, the hard timeout, the memory limits and scale-in waiting meanwhile, so the debugged thread takes no request; `debug status` shows the worker as `debugging`. `debug status` shows each worker's state (`starting`, `ready`, `debugging`, `replacing` for one a fresh worker takes the place of, `retiring` for one scaled in), whether the edge routes to it, and what each side it has holds as of the moment it answers (issue 369): THREADS, the requests holding an application thread of how many there are, and THREAD-OLDEST, how long the longest has held one, a request holding its thread from the moment a pool thread picks it up whatever the timeouts make of it, so one at `breakpoint()` or streaming counts; LOOP and LOOP-OLDEST likewise for the requests on the event loop of its concurrency, accepted WebSockets left out of both; SYNC, for a worker with a loop, the threads running synchronous code of the threads that may, for the fullest of the pools such code runs on (section 6.6: the loop's own, anyio's and asgiref's shared thread, each in the answer as sync_pools), counted whether or not the request that made the call is still in flight, and SYNC-OLDEST the age of the oldest request with a call on the loop's pool or asgiref's thread. The worker's table records each such thread against the request while the call runs, so `debug stacks` names the request on each `muru-sync` thread. The host asks each worker (`slots`, answered by the runtime's control thread without the interpreter, as the bookkeeping is), and one that does not answer within a second is shown from its last report, which carries the same figures, marked stale; the hard timeout keeps using the report's age of the oldest request that is not exempt. The table shows the columns of the sides any worker of the release has, every header one word, and `--json` carries `state`, `routed`, `threads`, `loop` and `stale`. `--dap` listens on `--listen` (127.0.0.1:5678) for one IDE and then attaches with `dap`, which in the worker starts debugpy's adapter on a loopback port (`debugpy.listen`), once, debugpy staying in the worker for later sessions, refused when debugpy cannot be imported, and relays bytes between a connection to it and the session, base64 in `attach_io`'s `data` both ways, muructl sending what the IDE wrote with each request and polling as for pdb; a breakpoint waiting stops at its caller's next line once the IDE has sent configurationDone, and the IDE disconnecting, `detach`, or the session's limits close the connection, which the adapter takes as the end, letting the code go on. `profile --path PREFIX` samples only the threads serving requests whose path (with its query) starts with the prefix, looked up in the runtime's requests in flight at each sample, and `--requests N` ends the profile once N of them have finished, a request counting as finished when it is no longer in flight, so one shorter than the interval may go uncounted; ASGI requests, which have no thread of their own, are not sampled this way, and neither a header to choose requests by nor the options on `trace` are offered. `--format pstats` (with `--output`) writes the merged samples in pstats' marshal format, each function `(file, first line, qualified name)` with the file's base name, its calls the samples it appeared in, counted once per sample however often it recurs, its own time the samples with it as the leaf and its cumulative time the samples it appeared in, each sample worth one interval, and each caller likewise. On Python 3.15 and later the host reads its workers from outside with `_remote_debugging.RemoteUnwinder` (PEP 768) wherever the operating system lets it, which is Linux; macOS needs root, so there and on older interpreters the worker is asked as before (ADR 0028). Python 3.14's unwinder stops where C code called into Python, losing the frames above a builtin such as `breakpoint()` or a callback such as `sorted(key=...)`, and the runtime's own above the application, so on 3.14 the worker is asked, and a worker that does not answer in time is then read from outside, its stacks short but better than none, with faulthandler's dump in the log as well; the capture before a hard-timeout kill goes the same way. The first read the system refuses is logged and the host asks from then on. Read from outside are `stacks`, whose answer carries `outside`, each thread's source line taken from the host's linecache, and the capture before a hard-timeout kill, and `profile` without `--path` or `--requests`, which the host samples on a thread of its own, the main thread left out, each frame labelled by the line it was running rather than the function's first line. Each application thread of a WSGI pool waits for work inside a Python frame of the runtime's, `muru._pool.serve_jobs`, which calls back into the runtime for its whole life and runs no bytecode meanwhile, since the reader cannot start from a thread parked at its interpreter's base frame, which a thread the runtime made otherwise is while it waits; threads with no Python frames, or waiting in that frame, are left out of stacks and profiles whichever way they are read. Names and requests come from the runtime's `bookkeeping`, which its control thread answers without the interpreter: the requests in flight with the thread serving each, and the names of the threads that tell the runtime theirs, which are the application threads, the event loop's thread and the threads of the loop's pools for synchronous code and of a gRPC mount's pool. On Linux a thread read from outside is known by its TID, and a thread the runtime does not name is named by the kernel, to which `threading` gives each thread's name as it starts and when it renames itself on Python 3.14 and later, cut to 15 bytes: the host reads `/proc/<pid>/task/<tid>/comm` as soon as it has read the frames, and once for each thread over a profile, the main thread being the thread whose TID is the worker's pid, and a name equal to the process's, which a thread nothing names inherits from the one that started it, counting as none. A thread neither names is `MainThread` when its innermost frame is the host's, else `thread-IDENT` (ADR 0053). A worker whose bookkeeping does not come within a second is shown without them. `tasks`, profiles with `--path` or `--requests`, and the soft timeout's capture stay inside. `memory --snapshot` keeps a tracemalloc snapshot in each worker (10 frames, tracemalloc started when off), replacing one kept before, `--diff` compares the present with it by line, keeping it, and `--drop` lets it go and stops tracemalloc when `--snapshot` started it; a `--diff` with none kept is refused. A traced worker stays in the sockets the host announces, so the edge routes to it as to any other and the trace counts the requests it serves meanwhile.

Development mode shows tracebacks in error pages and the terminal, and supports --single for running the whole application in one process under a debugger (section 13.1). The attach command is for what --single cannot cover: a bug that only shows with forked workers or real traffic, or in the release itself.

## 11.8 Times on log lines

Every line and record gets a time when Muru first handles it, whether or not that time is shown; showing it is a choice each output makes (ADR 0043).

- **What the time is.** An access record's time is when the request arrived. A Python logging record in the json format carries the time it was created. Any other line carries the time it reached the process that tags it: the host's relay for worker output, and the writer of Muru's own lines for those. Durations beside a time come from the monotonic clock.
- **Two forms.** A record uses the full form, RFC 3339 in UTC with milliseconds and a `Z` (`2026-11-02T05:42:22.836Z`), which sorts as text and parses the same everywhere. The short form, a clock (`16:42:22.836`), is in local time, because a clock without a zone is read as the reader's own; it is used only on a terminal. A short clock in UTC is never shown.
- **The order.** A line with a time starts with it, then the tag, then the message: `2026-11-02T05:42:22.836Z muru.worker[0]: WARNING demo: warned`. Muru's own lines are written by one helper that puts the time, the tag and the message in one write, and the daemon's tracing output uses the same layout.

| Output | Application and Muru lines | Access lines |
| --- | --- | --- |
| Standard output and standard error of a long-running command (`muructl run`, `muructl serve`, `muructl daemon run`) | no time; `--timestamps`, or `[logs] timestamps = true`, puts the full form in front of every line | their own time first: the short clock on a terminal, the full form otherwise; the full form on every line with `--timestamps` |
| Files (a release's log, `edge.log`, `daemon.log`, and standard output or error redirected to a regular file) | always the full form in front | JSON lines (`access.log`, or `--access-log-file PATH` under `muructl run`) with the full form in `time` |
| journald | no time, since journald stamps each line | the record's time as a field |
| JSON records, to any output | a `time` field in the full form, never a prefix | the same |
| `muructl logs` | the full form shown; `--no-timestamps` hides it | the same |
| The dashboard | a time column with the short clock in the viewer's local time and the full form on hover | the same, in the requests table |

- **No time on standard output by default.** A person at a terminal is watching lines as they happen, and a container runtime, journald or a supervisor stamps every line it collects, so a second time would be noise; the access line keeps its time because it is part of the request's record, as in other servers' access logs. `--timestamps` is for a supervisor that stamps nothing.
- **Files always carry it.** A process tells a file from a terminal or a pipe by what its stream is, so the daemon's and the edge's files, a release's log and a command's output redirected to a file are all files. A file is read after the fact, by `grep` and `sort` as well as `muructl logs`, and a time not written there cannot be shown later, so there is no setting to leave it out. A reader that does not want it hides it.
- **The dashboard's buffer keeps the time with each line**, as the access log's records do, rather than plain strings.
- **One output stream.** Under `muructl serve`, application, Muru and access lines all go to standard output, so they stay in order and a log collector does not treat every access line as an error for arriving on standard error.
- **Records a log collector keeps whole.** A collector splits records at newlines, so under `muructl serve --log-format json` each record is one line. A line of the application's output that is itself a JSON object, as Python logging's json format writes one (the default for Python logging under that flag), is the record, keeping its own `time`, with `kind` and `source` added, rather than a string inside another record. A traceback written to a stream arrives a line at a time; the host's relay gathers each source's traceback, from `Traceback (most recent call last):` to the exception's line with any chained exceptions, and writes it as one record, or as far as it got once nothing more has come for 200 ms. Every JSON line carries the pod's identity from the Downward API variables (`POD_NAME`, `POD_NAMESPACE`, `NODE_NAME` as `pod`, `namespace`, `node`) and OpenTelemetry's `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` (`service`, `resource`) when they are set.
