# gRPC services

```{admonition} Status
:class: note

gRPC mounts beside WSGI and ASGI, gRPC-only releases, the four kinds of
call over h2 and h2c, gRPC-Web, the health service and reflection.
Limiting h2c to trusted networks, CORS for gRPC-Web and per-mount thread
pools are still to come.
```

A release can serve gRPC services from the same workers as its WSGI or
ASGI application, or serve gRPC alone. Servicers generated by
grpcio-tools run unchanged: the entrypoint is a function that registers
them, as you would on a grpcio server.

```python
# svc/grpc_app.py
from svc.proto import greeter_pb2, greeter_pb2_grpc


class Greeter(greeter_pb2_grpc.GreeterServicer):
    def SayHello(self, request, context):  # runs on a thread
        return greeter_pb2.HelloReply(message=f"Hello {request.name}")

    async def StreamUpdates(self, request, context):  # runs on the event loop
        async for update in feed(request.topic):
            yield update


def register(server):
    greeter_pb2_grpc.add_GreeterServicer_to_server(Greeter(), server)
```

grpcio must be installed in the application's environment, since the
generated code imports it. It has no wheels for free-threaded Python, so
gRPC services need a regular build.

## A gRPC mount beside an application

A gRPC mount has an entrypoint and no path. Calls reach it by content
type and service name, so gRPC and HTTP share the listeners, hosts and
routes:

```toml
entrypoint = "svc.wsgi:application"

[mounts.api]
interface = "grpc"
entrypoint = "svc.grpc_app:register"
```

The same table goes under a release in an applied file, as
`[app.svc.release.r3.mounts.api]`. A request whose content type is
`application/grpc`, `application/grpc-web` or `application/grpc-web-text`
for a method the mount registered is a call; every other request goes to
the application as before.

## A gRPC-only release

```toml
[app.svc.release.r3]
interface = 'grpc'
entrypoint = 'svc.grpc_app:register'
processes = 2
threads = 8
reflection = true
```

A plain HTTP request to a gRPC-only release is answered 404. With
`muructl run`, `--interface grpc` does the same for a development run.

## Calls

All four kinds of call work: unary, server streaming, client streaming
and bidirectional streaming. A synchronous handler runs on one of the
worker's `threads`; an `async def` handler or async generator runs on
the worker's event loop. Each call is balanced across the workers on its
own, so one client connection spreads its calls over all of them.

Clients connect with HTTP/2 over TLS (h2) on an HTTPS listener, or over
plain HTTP/2 (h2c) on any listener. Request messages compressed with
gzip or deflate are decompressed at the edge; responses are sent
uncompressed.

The `context` a handler receives has the commonly used parts of
grpcio's: `abort`, `abort_with_status`, `set_code`, `set_details`,
`invocation_metadata`, `send_initial_metadata`, `set_trailing_metadata`,
`time_remaining`, `is_active`, `add_callback` and `peer`, which is the
client address after trusted proxy handling. An asynchronous handler's
context has the grpc.aio forms, with `read`, `write`, `cancelled` and
`add_done_callback`.

## Status and deadlines

| What happens | Status |
| --- | --- |
| The handler returns | OK, or what `set_code` set |
| The handler calls `abort` | the status it gives |
| The handler raises | UNKNOWN, "Exception calling application: ..." |
| No mount registered the method | UNIMPLEMENTED |
| The call's grpc-timeout passes | DEADLINE_EXCEEDED |
| A unary call runs past the request deadline or the soft timeout | DEADLINE_EXCEEDED |
| A streaming call's worker sends nothing for the idle timeout | DEADLINE_EXCEEDED |
| No worker takes the call within the queue timeout | UNAVAILABLE |
| A request message is over `max_body_size` | RESOURCE_EXHAUSTED |

When the client cancels a call or goes away, an asynchronous handler's
task is cancelled and a synchronous handler's `context.is_active()`
becomes false.

## Health and reflection

The edge answers the standard health service, `grpc.health.v1.Health`,
for the release (the empty service name) and for each registered service:
SERVING while the release has workers. `Check` answers NOT_FOUND for a
service nobody registered. `Watch` sends the status and stays open.

`reflection = true`, on the release or in the `[tool.muru]` table, serves
server reflection for every registered service, so tools such as grpcurl
can list and describe them. It needs grpcio-reflection installed.

## gRPC-Web

Browsers call the same services with gRPC-Web. The edge translates
`application/grpc-web` and `application/grpc-web-text` calls over
HTTP/1.1 or HTTP/2, with the status and trailing metadata in a frame at
the end of the body. Routes and policies, rate limits, client classes and
authentication sub-requests apply to gRPC calls as to any other request.
